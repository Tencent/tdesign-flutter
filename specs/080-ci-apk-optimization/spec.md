# CI 与 Demo APK 构建优化

## 背景与目标

PR 的相同 SDK APK 重复构建，平台矩阵反复生成资源，网站与 APK 串行。只在本轮减少重复工作，保留双 SDK、release 和现有回归口径。

## 最终方案

- 在 Flutter 3.32.0 集中生成 API、示例片段和构建信息，以工作流内 Artifact 传给各平台；不同 SDK 不共享依赖与编译目录。
- PR 的最低版本 APK 同时用于兼容验证和下载，latest APK 仍由 test-build 验证；develop push 保留双版本 APK。Web 和 APK 在资源准备后并行。
- APK 只执行普通 flutter build apk --release，保留 Flutter 默认依赖解析和原生插件准备，不增加独立 pub get、--no-pub 或双版本锁文件分支。
- Gradle 保持 8.14，仅将 all 分发改成 bin；增加 Gradle 缓存并使用现有 JDK 17，NDK 跟随 SDK。Android 工程除此两处以外维持基线。
- 包内版本号沿用原日期方案，下载文件名沿用组件版本与工作流运行编号。Example 锁文件继续忽略，自定义版本序号及依赖锁定不属于本轮。
- l10n 明确输出到 lib/l10n，不声明废弃 synthetic-package 选项。保留 ARB、导入和 generate: true，不升级工具链。

## 取舍与兼容

保留两个工作流分别准备资源，避免跨运行 Artifact 来源与权限耦合。版本号同日重复、版本资源丢失时旧回退和依赖复现问题仍然存在，后续独立修复；本轮不以减少代码为由删除必要插件准备。

## 验收标准

工作流语法和预览元数据格式正确；移出版本号与锁文件方案后，两个 SDK 的普通 release APK 重新构建成功，包内版本符合原方案。资源复用、功能及 Golden 入口保持；本地验证不代替精简版未来的远端 CI。

## 文档审计测试提速（本地后续修复）

将审计逻辑提取为显式接收包根目录和输出目标的函数，命令行入口仍根据脚本位置确定根目录并设置退出码。现有全部契约用例改为同进程调用，每次调用独立创建解析缓存，不改变进程工作目录、全局退出码或审计规则。保留真实子进程验证 JSON 成功、文本失败和参数错误；覆盖组件筛选与 manifest 同步。CLI 参数、输出格式与退出码保持兼容，不升级依赖或工具链，不改变 CI 调度范围。

验收：双 SDK 原有断言全部通过；CLI 与直接调用输出及退出码一致；无跨调用状态泄漏；记录同机前后耗时，不能将本地差异直接宣称为远端 CI 收益。

## 功能回归任务并行拆分（本地后续优化）

将双版本串行 test job 分为组件覆盖率、示例功能、工具与契约检查三类独立任务；测试类型与 Flutter 3.32.0/latest 组成独立 runner，组件再按下节分组，使用各自 checkout。所有原有测试命令、排除标签及逐组件覆盖率检查不变，不合并覆盖率文件，不拆分组件清单。保留原 test 检查名称作为汇总门禁，只有全部功能测试分支 success 才通过；失败、取消或跳过不得被汇总为通过。功能回归的完成时间由最长分支决定，不减少测试内容。

先在独立本地副本完成双版本验证，不升级工具链；后续按用户授权提交到 PR #1179，再测量远端并行耗时。

## 按组件名固定分两组

组件回归与 Golden 使用同一个固定函数：组件名 UTF-16 字符编码之和取模 2，再加 1，得到组号 1/2。组件名不变则归属不变，新增、移除其他组件或清单排序变化都不影响其组号。只维护现有 component_test_manifest.dart，不新增组件分组字段或耗时数据表。组内保留原清单顺序；不保证两组耗时均衡。

组件与 Golden 入口增加 --shard=1/2，无参数保持完整执行。逐组件测试、独立覆盖率 >=95%、Golden 固定 Flutter 3.32.0 Linux 和精确比较不变。Golden 必须先全局按原 executionKey 去重，再按首个声明的组件归属分组；跨组不能重复执行共享套件。同一组件的非共享视觉套件保持在同一组。失败退出码及 CLI 参数校验保留。

CI 组件分支为两个 SDK 各两组；示例和工具不重复分组。Golden 两组独立 runner、独立 failure artifact；保留原视觉检查名称作为汇总门禁，任一失败/取消/跳过不能通过。原功能汇总门禁继续等待全部功能分支。先在独立本地副本完成验证；后续按用户授权推送到 PR #1179 并核实远端结果与耗时。不更新 Golden 基线、不升级工具链。

## 片段一致性与 API 生成提速

在双版本 tooling 任务中对原 checkout 执行一次示例片段 --check；不下载或预先重生成片段，保留结构与片段静态分析。过期片段必须失败，资源准备任务仍生成构建资源。

API 生成继续使用已解析依赖中 tdesign_flutter_tools 的 SmartCreator 与 CommandInfo，不复制解析或 Markdown 规则。Node 保留清单校验及 dry-run；正常执行将任务一次传给 Dart 入口，逐组件新建生成器并 await，遇错中止。--check 继续生成到临时目录并逐字节比较，不写回仓库；dart run 保留冷启动依赖准备。不跨 SDK 共享解析或缓存，不升级工具链。双 SDK 对比原 CLI 与新入口全部 57 份文档字节及端到端耗时。
