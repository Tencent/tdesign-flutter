# 设计与实施方案

## 阅读路径

- 从站点“开始 → 0.2.7 → 1.0 迁移”进入：升级前准备 → 全局迁移 → 按组件迁移 → 业务验收。
- 从组件页进入：简短升级提示 → 当前组件专章 → 当前组件 API。
- 从旧类名进入：旧公开声明索引 → 对应组件章或公共能力说明 → 明确处置。

## 统一指南结构

保留一个物理文件，用目录、稳定锚点和章节组织，避免把383 项名称索引放在首次阅读的主体前方。

```text
从 0.2.7 升级到 1.0
├─ 适用版本与升级前准备
├─ 推荐升级顺序
├─ 全局迁移：导入、主题、文字、样式、资源与平台要求
├─ 组件速查表：组件 / 旧入口 / 新入口 / 迁移详情
├─ 组件迁移详解：57 个独立章节
│  └─ 每章使用下述统一模板
├─ 业务验收清单
├─ 常见迁移问题：简短回答，链接回详解
└─ 附录：0.2.7 公开声明处置索引
```

现有“受控值”“浮层确认”“主题优先级”等通用解释保留在全局说明或共同机制章节，组件专章链接引用，避免重复。现有九组可运行示例继续从 fixture 提取；覆盖到多个组件时，各章节链接到实际示例，不能把一组示例计作多个组件的完整验收。

## 组件页样稿：Button

提示块位置：组件介绍之后、“代码演示”之前。使用站点现有排版、提示色和普通链接；窄屏顺序排列，链接可换行，代码名不撑破容器。无需新增第三个页签或持久关闭状态。

> **从 0.2.7 升级**
> `TDButton` → `TButton`
> • `text` 改为 `child`；`onTap` 改为 `onPressed`。
> • `type/theme` 分别改为 `variant/colorPreset`。
> • 状态样式使用 `ButtonStyle`；未传 `onPressed` 表示禁用。
> 查看 Button 完整迁移说明 → `/flutter/migration-1-0#migration-button`

此样稿是信息和文案设计，实际交付时由根指南摘要生成。当前组件页 README 不添加这段手写正文。

## 接入现有生成链路

推荐在 `tdesign-site/site/plugin-tdoc/transforms.ts` 的 `before` 阶段，利用已有组件文件路径识别结果，注入从指南提取的提示块，再交给现有示例与 API 转换。

- 新增迁移摘要读取模块，输入规范化组件 slug 和站点指南副本；只允许白名单 slug。
- 渲染时以组件文档路径判断，普通文档和迁移指南本身不注入。
- 在正文“代码演示”之前注入一次；开发热更新重跑也不能累积提示。
- 根指南中的摘要标记、章节锚点、目录与链接由同步步骤检查；缺失、重复、空内容、超出三条摘要均报错。
- 摘要标记内容使用受控 Markdown 文本，不执行任意组件或代码。
- `page-contract.mjs` 继续校验原始页面正文，不放宽其禁止手写迁移段落的约束。渲染测试另验一次提示及正确目标。
- 当前 `scripts/sync-readme.mjs` 继续同步根指南到包内和站点；未来改动仅扩展摘要/锚点校验，不改 CI 配置。
- 历史 `specs/058-release-preparation/component-migration-index.json` 是审计基线，不作为第二份长期维护正文。实施时以根指南章节产生运行期映射；本目录映射只供设计核对。

## 命名与链接规则

设计矩阵见 `component-entry-matrix.json`。其中 `guideAnchor` 为待创建目标，`implemented: false` 明确表示尚未上线。源 slug 的下划线通常变为连字符；`backtop → back-top`、`sidebar → side-bar`、`refresh → pull-down-refresh` 必须显式映射。尤其区分 `TDTabBar → TTabsBar` 与 `TDBottomTabBar → TTabBar`，不得机械改前缀。

站点入口使用站内路径，根指南和包内目录使用 `#migration-...`。返回当前 API 使用组件站点完整 URL，以便包内和 GitHub 阅读也能访问。实际站点基地址与浏览器路由需在构建后的预览验证，不能只检查字符串。

## 内容补齐顺序

1. 先完成全局主题/文字、Button、输入与受控组件、Form、Picker/日期、Popup/Dialog/Toast、Upload、两种 TabBar、Swiper：优先避免编译错误和行为变化。
2. 补齐剩余组件的独立章节，对参数、枚举、回调、默认行为和移除类型逐项审查，复用已有证据但不复制不适用结论。
3. 把383 项旧声明索引逐条链接至具体章节；原来的“按组件重写”等泛化说明必须补充实际方向，能力无等价时直说。
4. 再接入自动摘要、站点往返链接与 FAQ；完成整体浏览和迁移验证。

## FAQ 设计

仅保留跨组件高频问题：为什么不能直接替换 TD 前缀；为什么编译通过但值不变化；为什么 Material Theme 不再改变 TD 默认样式；为什么找不到旧 DatePicker/Swiper/内部 State；加载 Toast 为什么需要明确持续时长。每题给简短答案并跳转对应章节，不再复制参数表和整段代码。

## 验证策略

文档结构校验覆盖57 章、唯一锚点、摘要与站点页面映射、旧声明处置链接、同步副本一致性。生成链路测试覆盖非组件页不注入、每页只注入一次、错误 slug 和缺失章节报错、现有手写正文仍被拒绝。执行现有站点示例/API 测试及生产构建。

新旧代码分别在0.2.7 和1.0 独立消费环境分析、运行，1.0 使用最低和当前稳定 SDK。按实际示例验证受控回写、确认/取消、禁用、异步退出和资源释放；已有九组及21 个消费测试是复用起点，不能声称覆盖57 个组件。

浏览器验证组件入口和指南目录的深链接、前进/后退、刷新定位、返回 API、桌面与375px 窄屏、键盘访问。纯文档结构设计无需执行 Flutter 全量回归；实施涉及组件或示例源码后按实际范围补充对应回归。视觉证据仍遵循原有 Linux Golden 约束。
