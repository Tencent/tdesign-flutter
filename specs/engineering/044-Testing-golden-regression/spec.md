## 背景与目标

以下保留设计形成时的问题与依据；已修复的问题不表示当前代码仍有同一缺陷。

Golden 覆盖和执行归属分散会使图片存在却未被 CI 运行，重复拼盘也使失败难以归责。


## 范围与非目标

覆盖本工程职责的设计与验收边界；不将目录整理扩展为新的组件能力、发布动作或远端配置修改。

## 最终方案与行为契约

### 覆盖与执行

1. 每个已登记组件至少保留初始公开页面的 light/dark Golden。
2. 真实操作后出现且能稳定停留的视觉状态必须通过真实手势触发，并分别保存 light/dark Golden。
3. 瞬时动画只在其视觉本身属于组件契约时保存；测试先创建并保持手势或精确 `pump` 到指定时点，不使用 `pumpAndSettle` 跳过动画。
4. 无限动画、平台纹理、系统输入法或仅回调结果由功能测试负责，并在覆盖矩阵说明不截图原因。
5. Golden 更新只在 Linux Flutter 3.32.0 环境进行，更新后使用相同命令无更新参数复跑。
6. 新增的视觉测试必须登记到对应组件的 `visualTests`，功能断言仍由双版本 example regression 执行。
7. 所有 Golden 使用 Flutter 默认精确比较器，禁止像素比例容差；空格、标点、字形、位置或颜色造成的任意像素变化都必须使测试失败。
8. 每个公开 API 组件必须拥有 `VisualTestKind.demo` 类型的视觉套件，且组件目录至少包含同名状态集合的 light/dark PNG；组件聚焦快照使用 `VisualTestKind.component` 明确区分。
9. `example/test/**/*_golden_test.dart` 与 `test/components/**/*_golden_test.dart` 必须被视觉调度器反向登记；禁止保留“文件和 PNG 存在、CI 从未执行”的孤立测试。
10. 多个组件共同使用的组件 Golden 可以共享同一测试文件，但调度器只执行一次；每个消费组件仍保留可审计的归属。

### 归属与排错

- 每个 Golden 有明确的组件或跨系统契约所有权；独立组件不拼成无归属的共享大图。单组件多状态矩阵和明确的 Material 隔离、消费者主题契约可保留。
- Demo Golden 与组件聚焦 Golden 分别登记，不能以一类替代另一类；测试文件和 PNG 存在不等于 CI 已调度。
- 公开 Demo Golden 固定 `TDESIGN_DEMO_TEST_MODULES=false`，不包含调试验证区块；组件 Golden 不受 Demo 区块开关影响。
- 字体缺字必须修复真实的页面字体依赖，不接受缺字基线；平台字体差异、配准展示与真实页面几何分开判断。
- 比较时记录基线、精确差异和当前图；新增/删除基线也必须登记。设计对比不得通过缩放或位移掩盖实际布局问题。
- 先无更新比对、逐项确认差异，再在项目约定的 Linux 环境更新，随后无更新参数复跑。不得使用宽松比较器、批量接受未知差异或在 macOS 上更新权威基线。

### 文档边界

本 Spec 只维护 Golden 知识。功能测试、覆盖率和通用 CI 登记维护在 [贡献规范](../../../CONTRIBUTING.md#组件测试与-ci-回归门禁)，不再保留通用测试清单或阶段性测试修复 Spec。

## 关键决策与取舍

| 决策 | 理由与取舍 |
| --- | --- |
| 采用的方案 | 以公开稳定视觉状态和明确的组件所有权组织基线，使用真实手势及精确像素比较。 |
| 保留的边界与代价 | 不接受宽松容差来消除未知差异；短期维护成本高于批量接受基线，但保留了回归可信度。 |

## 兼容性与迁移

本次只整理设计记录，不据此新增 API、改变默认值或判断全部兼容。后续接口删除、类型收紧或默认行为变化按最终源码和迁移指南核对。

## 验收标准

- 公开稳定交互态具有成对明暗基线，所有 Golden 文件进入调度且有可审计归属。
- Linux 约定 SDK 使用默认精确比较器；更新后无更新参数复跑，未知差异不直接接受。
- 功能、组件聚焦、Demo 与设备验证的范围分别说明，不用一个入口代替全部覆盖。

验收标准描述应满足的行为，不表示已执行或通过；执行范围与证据见 [acceptance.md](./acceptance.md)，剩余事项只在 [tasks.md](./tasks.md) 维护。
